# Ак-Бата Admin — автотесты (Playwright)

E2E-тесты для админ-панели сервиса доставки воды «Ак-Бата»:
https://admin.akbata.i7.kg/

**145 тестов в 19 файлах** (см. `npx playwright test --list` для точного числа), покрывающих логин, заказы, товары (включая полный цикл
создание → редактирование → удаление), категории, услуги, покупателей (физ. и юр. лиц),
пользователей, акции, тарифы и заявки на тарифы, настройки, доставку и профиль. Полная карта того, что именно проверено — в
[TESTS_CHECKLIST.md](./TESTS_CHECKLIST.md). Начните с него, если пришли в проект
впервые.

## Стек

- [Playwright Test](https://playwright.dev/) + JavaScript (без TypeScript)
- Page Object Model — вся логика взаимодействия со страницей лежит в `pages/`,
  тесты в `tests/` только описывают сценарий
- `dotenv` — секреты (логин/пароль) не хранятся в коде

## Быстрый старт

### 1. Установка

```bash
npm install
npx playwright install chromium
```

### 2. Настройка окружения

Скопируйте `.env.example` в `.env` и впишите реальные логин/пароль от админки:

```bash
cp .env.example .env
```

```
ADMIN_URL=https://admin.akbata.i7.kg
ADMIN_LOGIN=логин
ADMIN_PASSWORD=пароль
```

`.env` в `.gitignore` 

### 3. Запуск тестов

```bash
npm test                 # все тесты, headless
npm run test:headed      # с открытым браузером — удобно смотреть, что происходит
npm run test:ui          # интерактивный UI-режим Playwright (лучший способ отлаживать)
npm run test:debug       # пошаговая отладка с инспектором
npm run report           # открыть HTML-отчёт последнего прогона
```

Запуск конкретного файла:

```bash
npx playwright test tests/login.spec.js
```

Запуск одного теста по названию:

```bash
npx playwright test -g "Успешный вход"
```

> Тесты выполняются строго последовательно (`workers: 1`, `fullyParallel: false` в
> `playwright.config.js`). Это осознанное решение: часть сценариев (создание
> заказа/товара/покупателя/категории/пользователя) пишет реальные данные в БД, а **новый
> вход тем же аккаунтом отзывает старые токены** — параллельный запуск (или два прогона
> одновременно) роняет сессии соседних тестов. Не запускайте два прогона одновременно.

## Как писать новый тест — минимальный чек-лист

1. Найдите/создайте Page Object в `pages/` для нужной страницы (или дополните
   существующий, если такой уже есть — см. TESTS_CHECKLIST «Не покрыто автотестами»).
2. В конструкторе Page Object — только локаторы, никакой логики.
3. Методы (`goto`, `fillX`, `clickY`) — действия, которые тест будет вызывать.
4. Тест в `tests/*.spec.js` — только последовательность вызовов методов и
   `expect(...)`, без прямых селекторов, если это возможно.
5. **Перед тем как писать локаторы вслепую — прочитайте раздел «Известные нюансы
   сайта» ниже.** Половина времени, потраченного на этот проект, ушла на отладку
   именно этих особенностей.
6. Прогоните новый тест минимум дважды подряд, прежде чем считать его готовым —
   часть страниц подгружает данные асинхронно, и тест, прошедший один раз, может
   быть флакующим.

## Известные нюансы сайта

Эти особенности несколько раз ломали тесты, написанные "в лоб" по видимому тексту
на странице. Знание о них экономит часы отладки:

- **Сайдбар свёрнут и раскрывается только по hover.** Пункты меню "Товары",
  "Услуги", "Тарифы", "Покупатели", "Акции" спрятаны в подменю "Магазин", текст
  которого имеет `display:none`, пока курсор не наведён на сайдбар (не клик!).
  Используйте `utils/nav.js` → `openShopSubmenu(page)` перед кликом по таким
  ссылкам. После клика сайдбар остаётся раскрытым и может перехватывать клики по
  контенту — уводите курсор: `await page.mouse.move(600, 400)`.
- **Некоторые `<select>` подгружают опции асинхронно.** Например, фильтр
  категории на `/products` и фильтр статуса на `/orders` в момент рендера
  страницы имеют 0-1 опцию, а полный список появляется чуть позже. Проверяйте
  `select.options.length > 1` через `page.waitForFunction(...)` перед
  `selectOption()` — см. `orders.page.js` → `filterByStatus` как пример.
- **После сохранения товара приложение остаётся на форме `/add-product`** —
  редиректа нет. Успех подтверждайте ответом API: `POST /api/products` → 200 и
  `data.id` (см. `ProductFormPage.saveAndWaitForApi()`). Для заказа тест
  `order-create.spec.js` ждёт `/edit-order/:id` — это не перепроверено.
- **Обязательные заголовки на трёх языках.** У товара и категории заголовок
  обязателен для RU, KY и EN — при сохранении с одним RU приходит 422.
- **Поиск в списках работает только по кнопке-лупе** (`button.input-group-text`),
  ввода текста недостаточно. Формат запроса: `where=field(like)%value%`.
- **Удаление** — кнопка корзины → модалка → "Удалить навсегда" → `POST /api/<сущность>/:id`
  (204). Дожидайтесь этого ответа, иначе поиск и удаление гоняются друг с другом.
- **Текст валидации зависит от языка сессии**: после входа через UI — русский, при
  восстановленной сессии — английский ("The field is required."). Используйте
  `REQUIRED_FIELD_TEXT` из `utils/auth.js`.
- **Навигация по прямым URL.** Наведение на сайдбар нестабильно, поэтому страницы
  открываются через `page.goto('/products')` и т.п.
- **"Способ доставки" / "Способ оплаты" / "Статус оплаты" в форме заказа**
  визуально показывают первую опцию как выбранную, но реальное значение (v-model)
  остаётся пустым, пока оператор не выберет его вручную. Чтобы тест дошёл до
  сохранения — выбирайте эти поля явно (`selectOption(...)`), не полагайтесь на
  визуальный дефолт.
- **`waitForLoadState('networkidle')` не всегда достаточно.** Некоторые таблицы
  (например, список компаний) дорисовывают строки уже после того, как сеть
  затихла. Надёжнее дождаться реального появления строки:
  `await tableRows.first().waitFor({ state: 'visible' })`.
- **Не всё в интерфейсе на русском.** У части сущностей (услуги "lift" и
  "damaged_bottle", тип клиента в заказах) текст на английском при том, что
  остальной интерфейс полностью русифицирован — если тест не находит ожидаемый
  русский текст, сначала проверьте, не один ли это из этих случаев.
- **Сессия переиспользуется.** `loginAsAdmin` сохраняет состояние в `.auth/admin.json`
  и в течение 20 минут подставляет `token`/`user` в
  `localStorage`, предварительно проверив токен запросом к API (401 → вход через UI заново).
  Причина: сайт "душит" частые логины таймаутами. `login.spec.js` использует `LoginPage`
  напрямую и общую сессию не трогает. `global.setup.js` по-прежнему не подключён.
- **Песочница периодически недоступна.** Фронтенд `admin.akbata.i7.kg` может отвечать,
  когда API `https://ak-bata.i7.kg/api` уже не отвечает вообще (таймаут). Тогда падают
  *все* тесты на входе или на `networkidle` — это не дефект тестов. Проверка:
  `curl -m 15 https://ak-bata.i7.kg/api/categories`.
- **`waitForLoadState('networkidle')` может не сработать вообще** на тяжёлых страницах
  (например, список компаний — 1700+ записей) и съесть весь таймаут теста. Если тест
  зависает ровно на `test.timeout` без внятной ошибки — подозревайте это в первую очередь;
  замените на `waitForResponse` по конкретному API-запросу с `.catch(() => {})`.
- **Поиск (`where=field(like)%значение%`) может не фильтровать вообще**, отдавая тот же
  список, что и без фильтра — подтверждено напрямую через API минимум в категориях,
  пользователях и услугах. Проверяйте фактическое поведение перед тем как писать тест
  «поиск находит нужную запись» — возможно, нужно писать тест на дефект вместо этого.

## Известные баги продукта (не тестов)

Найдены автотестами, подтверждены вручную — стоит завести в баг-трекер, если ещё
не заведены:

1. **Фильтр статуса на `/orders` не работает.** Выбор значения в `<select>`
   корректно меняет и сам select, и URL (`?status=completed`), но таблица не
   фильтруется — показывает заказы всех статусов вперемешку.
   См. `tests/orders-list.spec.js` (тесты оставлены с ожиданием *правильного*
   поведения — позеленеют после фикса).
2. **Поля "Способ доставки"/"Способ оплаты"/"Статус оплаты" на `/add-order`**
   визуально выглядят выбранными (первая опция), но их фактическое значение
   пустое, пока оператор не кликнет вручную — при этом поля обязательные.
   Стоит проверить, что бэкенд не принимает заказ с пустыми значениями молча.
   См. `tests/add-order.spec.js`.
3. **EN/RU-несогласованность контента**: заголовки услуг "lift"
   ("Floor delivery (no elevator)") и "damaged_bottle" ("Damaged/lost bottle"),
   а также тип клиента в заказах ("Individual") — на английском при полностью
   русском интерфейсе.
4. **Поиск на `/services`** — debounce работает нестабильно, иногда фильтрация
   не применяется в разумное время ожидания.
5. **Поиск пользователей по email** на `/users` всегда возвращает пустой список, даже для
   существующего email (`tests/users.spec.js`, тест помечен "(дефект)").
6. **Поле "Пароль" в форме пользователя** не помечено `*`, но обязательно (422).
7. **Валидация зависит от языка сессии** — русские тексты после входа через UI, английские
   при восстановленной сессии.
8. **Поиск не фильтрует результаты.** Подтверждено напрямую через API (`where=title(like)...`
   возвращает тот же список, что и без фильтра) минимум в трёх разделах: категории,
   пользователи (по email — см. п. 5) и услуги. Похоже на общую проблему обработки `where`
   на бэкенде, а не баг конкретной страницы.
9. **Создать компанию через `/companies/add` невозможно.** Поле ИНН недоступно для ввода
   (задизейблено и до, и после заполнения названия), а обязательного на бэкенде `user_id`
   в форме нет вовсе — `POST /api/companies` всегда отвечает 422. См. `tests/companies.spec.js`.
10. **⚠️ (29–30.09.2026) Таблицы `orders` и `companies` в базе песочницы пусты.**
    `GET /api/orders` → `{"data":[]}`, `GET /api/companies` → `meta.total: 0` — при этом
    ранее (несколько дней назад) там были сотни реальных записей. Товары и категории не
    пострадали. Похоже на потерю данных — сообщено разработке отдельно, требует проверки
    бэкапов. Пока это так, тесты на компании/заказы, зависящие от реальных данных
    (не создающие свои через API/форму), недостоверны.

## Тестовые данные

Для `order-create.spec.js` используется реальный существующий в БД клиент:
телефон `+996555666777` ("Auto Test"), адрес `Токтогула, д. 126`. Если этот
клиент/адрес будет удалён из продакшена/тестового окружения — тест начнёт падать
на шаге поиска клиента, это ожидаемо и не баг кода теста.

`categories.spec.js`, `users.spec.js`, `product-crud.spec.js` и `product-create.spec.js`
создают запись с уникальным именем (`Date.now()`) и удаляют её в `finally`, даже если тест упал.

`customers.spec.js` создаёт покупателя с уникальными телефоном/email на каждый
запуск (`Date.now()`) и **сам удаляет его** в рамках теста — новых тестовых
покупателей после прогона в БД оставаться не должно.

## Troubleshooting

- **Все тесты падают с `Cannot find module`** — проверьте, что путь в
  `require()`/`import` совпадает с реальным именем файла в `pages/` (регистр
  важен: `Services.page.js`, но `products.page.js`).
- **Тест падает с `strict mode violation: resolved to N elements`** — значит
  локатор слишком широкий (обычно `getByText` без `{ exact: true }` ловит
  случайные совпадения, например "ID" совпадает с "Individual"). Сузьте
  локатор, при необходимости — до конкретного родителя (`thead`, конкретная
  строка таблицы и т.п.).
- **Тест иногда падает, иногда проходит** — почти всегда это один из пунктов
  выше («Известные нюансы сайта»): или сайдбар, или асинхронная подгрузка
  опций/строк. Добавьте явное ожидание нужного состояния вместо `waitForTimeout`.
